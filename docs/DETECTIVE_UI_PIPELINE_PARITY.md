# Pipeline2 → unified workspace: parity and transition

Review date: 5 November 2026. Scope: the Detective-UI worktree, including its current pipeline bridge. This is an implementation audit, not certification of every scientific, remote or classifier path.

## Accepted direction

The compact Pipeline widget and a larger dockable Pipeline Editor are two views of the same definition, effective run configuration and selection. The larger editor will progressively replace the pipeline2 frontend. It must preserve the capabilities and interaction rules developed in pipeline2; replacing its window does not justify reducing its functionality.

The current Pipeline Designer and Advanced windows still instantiate pipeline2. They are transitional compatibility paths, not a delivered replacement editor. Keep pipeline2 available until the corresponding parity gates below have passed. Reuse or extract its catalogue, parameter, binding and orchestration mechanisms instead of implementing a second engine.

Image is the shared contextual viewport. An editor can be docked, floating or larger without acquiring a second scientific image context. Defining/testing ROIs from a pipeline must activate the main-image assistant with an explicit project, FOV, frame/channel, module and draft identity. The independent Define ROIs action remains available outside pipelines.

## Status vocabulary and source map

- **Native**: the stated capability has a new-UI entry point and implementation.
- **Partial**: only the stated subset has been migrated.
- **Bridge**: the capability remains available through pipeline2, not through a replacement editor.
- **Pending**: no independent new-UI implementation is present.

Primary sources: [pipeline2](../structure/GUI/pipeline2_extracted.m), [PipelineWidget](../structure/GUI/+detecdivui/PipelineWidget.m), [PipelineGraph](../structure/GUI/+detecdivui/PipelineGraph.m), [RunSetup](../structure/GUI/+detecdivui/RunSetup.m), [RunDraft](../structure/GUI/+detecdivui/RunDraft.m), [ROIWidget](../structure/GUI/+detecdivui/ROIWidget.m), [Viewer](../structure/GUI/+detecdivui/Viewer.m), [ProjectRuns](../structure/GUI/+detecdivui/ProjectRuns.m). Method names below identify the reusable behavior rather than treating the existence of a backend as evidence of migrated UI support.

## Workflow image entry points

There are two direct workflow2 constructors in pipeline2: `editRoiPatternDraft` and `openWorkflowRoiEditor`. Their user-facing callers include pattern Create/Test, general ROI definition editing, manual drawing and tracked ROI configuration. `confirmRoiPatternsForRun` also enters the pattern library before execution; its library Edit action must reach the central assistant.

`openRoiDefinitionEditor` can alternatively call package `.ui` frontends. In particular, [roiTracked.ui](../engine/dataloading/+roiTracked/ui.m) still constructs legacy `workflow`. The unified UI must intercept these image-editing requests before the legacy frontend is reached. `buildWorkflowProjectFromRawData` parses raw data into a temporary shallow via `addData`; it is image-context preparation, not a second drawing algorithm. Retain this capability explicitly when no existing project/FOV can supply the requested source.

The runtime bridge and definition-only designer now both supply `ViewerRoiCallback` through the same owner-validated request route. The latter's missing callback was corrected during this review. Module/run FOV selections, including named FOVs, select the main-image target. The independent designer does not become bound to the preview project. The editor remains available when a request cannot resolve its image context. The standalone legacy applications retain their old entry points for compatibility while the viewer path is migrated.

The crop scope remains an explicit open issue: the current bound assistant writes `project.fov(i).crop` when applying a definition, while the pattern backend reads that project property. Removing the write alone would silently change detection behavior. A run-local crop needs a supported backend contract, or the UI must expose project crop editing as such, with its own apply/save behavior. The target isolation rule below is not yet fully met for this property.

Pending module drafts are now stored separately from standalone drafts, by project/FOV and request identity (owner, module, template/run and effective configuration). The integration test alternates between two modules on the same FOV without losing their unsubmitted rectangles. A changed source/module invalidates its old reply. Accepted runtime-scoped ROI values update existing override records, preventing old frame/channel/FOV values from shadowing the accepted edit. Successful Use in Run/Pipeline dismisses that completed request; reopening starts from the accepted definition.

First-time raw-data mode still needs a temporary main-image source context using the legacy parser. For now, a requested raw path unrelated to the selected project/FOV is rejected with a selection status rather than borrowing its images. This is a known migration gap, not equivalent to the standalone parser workflow.

## Ergonomic and data invariants

1. **One scientific context.** Bind a request to owner/editor lifetime, pipeline/draft, module ID/type and source project/FOV/frame/channel. A change of project, module type, template or closed editor invalidates the old response. A floating editor must select or clearly expose its own requested image context rather than borrowing an unrelated visible FOV.
2. **One definition, several views.** Compact graph, larger graph, module dialog, run settings and main-image assistant share the same effective draft. Reopening a module preserves its pending edits. Parameter controls retain their pipeline2 roles, types, defaults, availability and dependencies.
3. **Preview, apply and save are different.** Drawing/testing changes a draft. Use in Run updates that draft, not project ROI/crop/results or pixel stores. Create ROIs, extraction, library save, template save, project save and execution remain explicit actions with their established scopes.
4. **History stays reproducible.** Editing a historical run forks its frozen effective configuration. Preserve source handles/files, run identity, exact overrides, selected modules and explicit graph connections. A type replacement must not regenerate unrelated links from visual positions.
5. **Progress belongs to the visible action.** Image parsing/preview uses Image/ROI progress; graph preparation uses Pipeline progress; active jobs keep their monitor/cancel owner. No startup raw-path search, implicit inference or Hub submission.
6. **Classic, contextual UI.** English labels, standard menus, context-menu graph operations, tooltips/status help and real docking. Show advanced controls when requested; do not remove them or fill the compact widget with permanent explanatory text.

## Cutover gates

1. **Secure the central-image bridge.** Cover runtime and definition editing; docked/floating editors; explicit FOV/frame/channel; missing-source relinking; standalone drawing; pattern library editing; cancelled/closed/switched-context callbacks; unchanged project state before explicit generation/save.
2. **Replace module editing without feature loss.** Extract shared catalogue/typed-parameter/binding/model-reference components. Exercise representative built-in, Python-backed, external and custom modules. Verify exact round trips for arrays, choices, structured references and static/runtime separation. Both compact and larger views use those components.
3. **Replace graph authoring.** Native add/insert/delete/change/fork/merge/reconnect, symbolic/resource links and rename handling must preserve stored topology and validation results on branched templates. Reopen/save/export parity is required, including independent design with no project.
4. **Replace run operations.** Equivalent validation, smoke tests, scope/policy confirmation, local/WSL/Hub launch, progress/cancel/reconnect, history and result refresh. Test on temporary fixtures and controlled reference acquisitions; no real dataset is changed merely to test UI navigation.
5. **Retire the default pipeline2 handoff only after parity review.** Record migrated matrix rows and evidence. Keep a legacy entry point for remaining supported workflows until their replacements are usable. A backend helper or a visible button alone does not satisfy a gate.

Existing regression entry points include `detecdivui.moduleEditingTest`, `pipelineGraphTest`, `projectRunsTest`, `pipelineSettingsTest`, `newRunTest` and `separationTest`. They cover useful subsets, not the full matrix or all remote/scientific behavior.

`detecdivui.recentPipelinesTest` checks the compatible MRU schema, lexical missing references, deduplication/cap, persistence and isolated in-memory history. `detecdivui.pipelineLibraryTest` checks Pipeline ownership, the always-visible Open/Recent tree and single-click opening, reuse of an open draft, missing-reference failure and continued project/run scope. `projectRunsTest` covers project-owned run browsing, frozen graph recall and editable forks. `RecentPipelinesFile` injects an in-memory or temporary MAT store for these UI tests. These layout changes do not replace pipeline2's advanced editor or execution controls.

`detecdivui.pipelineImageContextTest` uses two synthetic FOVs, frames and channels. It verifies the actual module ROI button, lazy pixels on the correct FOV, independent pending module drafts, changed/closed owner rejection, named run scope, effective frame/channel round trips, and independent design without a dataset or a Workflow window. Source TIFF pixels, existing ROI handles/pixels and absence of run/H5 creation are checked. This does not certify crop isolation, tracked-mask preview, first raw import or Hub execution.
